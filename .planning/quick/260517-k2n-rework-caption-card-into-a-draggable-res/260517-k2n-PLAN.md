<objective>
Rework the "Caption Card" feature into its target mental model: a **full-bleed photo background** with an **independent draggable/resizable colored rectangle layer** rendered on top of it and below the text.

The feature was iterated 4× today on the news-carousel `layout` mechanism, which works by *constraining/resizing the photo* (`layout: 'cover'|'body'` zones the photo to a half; `news_image_height` resizes it). The user has rejected that model. The photo must be a permanent full-bleed background; the caption card must be a real overlay rectangle the user moves and sizes ON the canvas.

Purpose: stop touching the photo. The card is "just a square" — enabled, color, opacity, height (via resize), vertical position (via drag + Top/Bottom snap). Nothing more.

Output:
- `resolveCaptionBar` (the existing `caption_bar_*` resolver, quick-260515-k12) GENERALIZED to carry `enabled` + free `x`/`y`/`width` geometry — reusing the proven shared-resolver + 3-path-parity machinery rather than inventing a new field family.
- A new `caption_bar_*` opacity already exists; add `caption_bar_enabled` + geometry fields to `SlideStyleOverrides`.
- The canvas renders the card as a draggable+resizable `<Rnd>` (editable branch) / plain div (non-editable branch).
- The Satori PNG path and the HTML export path render the same rectangle (the HTML path currently renders NO caption card — this plan adds it for true 3-path parity).
- The Caption Card panel keeps on/off + color swatches, ADDS an opacity slider, REMOVES the Photo-height slider, and repurposes Top/Bottom as snap presets.
- The OLD `CaptionBarControls` bottom-card panel is removed from `elements-panel.tsx` — the reworked panel now generalizes `caption_bar_*` to every template, so the old image-with-bottom-card-gated panel is redundant and would otherwise cause a conflicting dual-panel UX.
</objective>

<key_decisions>
These decisions are LOCKED by the planning context and codebase investigation — the executor implements them, does not revisit them.

1. **DATA MODEL — generalize `caption_bar_*`, do NOT invent a new field family.** `caption_bar_color` / `caption_bar_opacity` / `caption_bar_height_pct` / `caption_bar_position` already exist (slide.ts:217-220) and already have a shared resolver + canvas + Satori parity. Add exactly four new optional `SlideStyleOverrides` fields:
   - `caption_bar_enabled?: boolean` — the on/off state. The card renders iff this is `true`.
   - `caption_bar_x?: number` — left edge, percent 0..100. Default `0`.
   - `caption_bar_y?: number` — top edge, percent 0..100. Default derived from `caption_bar_position` (bottom => `100 - height`, top => `0`).
   - `caption_bar_width?: number` — width, percent 0..100. Default `100` (full-bleed width — "it's just a square", a full-width band is the simplest default).
   `caption_bar_height_pct` is REUSED as the card height (percent). `caption_bar_color`/`caption_bar_opacity` reused verbatim. `caption_bar_position` is REUSED purely as the Top/Bottom **snap preset** — clicking it rewrites `caption_bar_y`. This is the simplest shape covering {enabled, color, opacity, height, vertical position, draggable} with zero new structured objects.

2. **GATING — the caption card is NO LONGER gated on `backgroundMode`.** Today the `bottom-card` only renders for `image-with-bottom-card` templates (`useBottomCard`). The new card is a generic overlay available on EVERY slide. The render gate becomes `slide.style_overrides?.caption_bar_enabled === true` — independent of template. `useBottomCard` and the old `bottom-card` div are REPLACED by this new gate (see Task 2/3). A slide that never enabled the card renders byte-identical to today (no card div at all).

3. **CANVAS SELECTION — the card is selected/dragged by clicking its own body.** The card renders at `zIndex:2` (below text at `zIndex:10`). The `<Rnd>` wrapper has `pointerEvents:'auto'` so the user grabs the card by clicking any part of its colored rectangle NOT covered by a text box (the card is large; the text boxes are small — there is always exposed card surface). This mirrors how decorations are click-selected via `onMouseDown` on their `<Rnd>`. Selection is tracked by a NEW local `useState` in slide-preview (`captionCardSelected: boolean`) — the card is NOT an addressable layer with an id, so it does NOT enter the `Selection` model or the LayersPanel (keeping scope minimal — "don't overengineer"). When selected, 8 resize handles + a selection outline render at a HIGH `zIndex` (51, matching the decoration-selection chrome) so the handles are grabbable above the text. Clicking empty canvas or ANY other element deselects the card via a capture-phase handler (see Task 3, deselection step). The card stays VISUALLY at `zIndex:2`; only its selection chrome floats above.

4. **REMOVE the photo-constraining mechanism for this feature.** The "Photo height" slider (`caption-card-height` -> `news_image_height`) is DELETED from the panel. The on/off + Top/Bottom controls STOP writing `style_overrides.layout` — they now write `caption_bar_enabled` / `caption_bar_y`. The `layout` / `news_image_height` / `background_color` fields and the `newsZone` render machinery are LEFT IN PLACE (do not delete them — other code and existing slides depend on them) but the Caption Card panel no longer touches them.

5. **BACKWARD COMPATIBILITY — existing `layout`/`news_image_height` slides render unchanged; no migration.** A slide currently carrying `style_overrides.layout: 'body'` (the user's current screenshot slide) keeps that field. The `newsZone` render path (slide-preview.tsx:784-786, render-slide-satori.tsx:193, render-slide.ts:260) still honors it — those slides render exactly as they do today. The new caption card is purely additive: it only appears when `caption_bar_enabled === true`, which legacy slides do not have. We do NOT migrate `layout` slides into the new model and we do NOT reinterpret them — they are simply a separate, still-working legacy path. The new panel, when opened on a legacy `layout` slide, shows the caption card as OFF (its own `caption_bar_enabled` is unset); enabling it adds the new overlay on top of the still-zoned photo. This is acceptable (the user explicitly wants the new model going forward; the rare legacy slide keeps working). State this in the SUMMARY.

6. **3-PATH PARITY — add the caption card to the HTML export path.** `render-slide.ts` currently renders NO caption card. For TPLREND-05 the new overlay MUST resolve identically across canvas + Satori PNG + HTML. This plan adds the caption-card div to `render-slide.ts` (Task 4). All three paths import the SAME `resolveCaptionBar`.

7. **DUAL-PANEL COLLISION — remove the old `CaptionBarControls` panel.** `caption-bar-controls.tsx` (`CaptionBarControls`) is the OLD bottom-card panel; it writes the same `caption_bar_*` keys this rework now generalizes to all templates. Both it and `SlideBackgroundControls` mount in `elements-panel.tsx`'s `slideLevelCards`. After the rework, on `magazine-bold` / `tr3nding-news` templates BOTH panels would render and BOTH would write `caption_bar_*` — conflicting, broken UX. DECISION: the reworked `SlideBackgroundControls` SUPERSEDES `CaptionBarControls` (it now exposes on/off + color + opacity + Top/Bottom for the SAME `caption_bar_*` family, on every template — a strict superset of what the old panel did). Task 6 REMOVES `CaptionBarControls` from `elements-panel.tsx` (drop the import + the JSX mount) AND DELETES the `caption-bar-controls.tsx` component file and its `__tests__/caption-bar-controls.test.tsx` — a deleted component must not leave a dangling import or an orphan test, so the build stays green. The component is fully redundant; leaving it unmounted-but-present would be dead code, so deletion is the chosen path.
</key_decisions>

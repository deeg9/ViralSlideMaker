<objective>
Fix the photo-treatment toggle in the slide editor right rail. Today, clicking any treatment button (B&W Switch, Cream/Cobalt duotone, Subtle/Medium/Heavy grain) persists to the DB but never updates local React state, so the active button never flips and the preview image never changes until a hard refresh. `handleSlideTreatmentChange` in `slide-editor.tsx:101-108` calls `updateSlideTreatment` only — it must additionally dispatch `UPDATE_SLIDE` to the editor reducer.

Sister fix `quick-260502-fai` just shipped the same fix for three watermark handlers in the same file. This plan mirrors that pattern with one wrinkle: the treatment server action computes server-side fields (`background_url` for the treated photo, `derived_palette`). So this handler uses a **hybrid** strategy:
1. Optimistic dispatch BEFORE the server call: set `treatment_applied` and `grain_intensity` so the active button flips instantly.
2. Server-confirmed dispatch AFTER `updateSlideTreatment` succeeds: merge `background_url`, `original_source_url`, and `derived_palette` from the returned slide so the preview swaps to the treated image.

Purpose: Restore the photo-treatment UX. Currently the entire treatment surface looks broken (buttons don't respond, image doesn't change) — pre-PMF this is a feature-killer.
Output: One patched handler + one new vitest file, mirroring the sister fix's structure.

Out of scope (do NOT touch):

- `photo-treatment-controls.tsx` — it correctly reads from `slide` props.
- Existing watermark handlers from quick-260502-fai — they are correct.
- Replace/remove the `// quick-260502-fai: NOTE — handleSlideTreatmentChange (below) has the same local-state-sync bug shape...` follow-up comment at lines 97-99, since this plan is the follow-up.

  kind: 'bw' | 'duotone-cream' | 'duotone-cobalt' | 'none'

  slideIndex: number,

): Promise<{ success: true; slide: Slide } | { success: false; error: string }>

The action mutates these slide fields server-side:
- `slide.original_source_url` (back-filled from background_url if null — STEP 1, D-27)
- `slide.background_url` (reset to original on 'none', or set to treated URL on bw/duotone)
- `slide.style_overrides.treatment_applied` (set to spec.kind, or undefined on 'none')
- `slide.style_overrides.derived_palette` (extracted from treated image, or undefined on 'none')
- `slide.style_overrides.grain_intensity` (always set to spec.grain — STEP 4, D-09)

From src/lib/editor/editor-reducer.ts (UPDATE_SLIDE case, lines 141-155):
```typescript
case 'UPDATE_SLIDE': {
  const slides = state.present.map((slide, i) => {
    if (i !== action.index) return slide
    const updated = { ...slide, ...action.updates }
    // Shallow merge of style_overrides only when both sides exist.
    if (action.updates.style_overrides && slide.style_overrides) {
      updated.style_overrides = {
        ...slide.style_overrides,
        ...action.updates.style_overrides,
      }
    }
    return updated
  })
  return pushHistory(state, slides)
}
```

CRITICAL — reducer's style_overrides merge is shallow. `updates.style_overrides = { treatment_applied: 'bw' }` ALONE would clobber sibling keys (watermark, hook_position, etc.) UNLESS the action carries the full spread. So both dispatches in this plan MUST pass `style_overrides: { ...(currentSlide.style_overrides ?? {}), <changed keys> }` — same pattern the watermark fix uses.

# Quick Task 260427-vm2: Hero PNG cleanup

## Context

v2.4 ships hero thumbnails to a public Supabase Storage bucket on publish, but
neither the row delete (RLS-gated `DELETE FROM published_carousels`) nor the
soft-delete `unpublish_carousel` RPC clean up the storage file. Every
unpublish/delete leaks one PNG. Tested live during /gsd-autonomous wrap-up —
confirmed real bug.

## Approach

A two-step server-action wrapper that pairs row deletion with storage cleanup.
The Postgres row is the source of truth; storage is best-effort cleanup
afterwards (so a failed storage call doesn't leave a row pointing at a missing
image).

Out of scope (deferred):
- A nightly orphan-sweep `pg_cron` that finds storage objects with no matching
  `published_carousels.hero_image_url` (defense-in-depth against admin-direct
  DELETE FROM Supabase Studio). Worth doing but is its own task.
- Properly implementing republish (PUB-06) with hero regeneration. The
  Manage Published dashboard view was deferred from Phase 30.

## Tasks

### Task 1: `deletePublishedCarousel(publishedId)` server action

**File**: `src/app/(dashboard)/project/[id]/publish-actions.ts`

Add `deletePublishedCarousel(publishedId: string)` that:
1. Validates the user owns the row (extra defense — RLS already enforces this)
2. Reads `hero_image_url` from the row
3. Parses the storage path out of the public URL (everything after
   `/object/public/hero-thumbnails/`)
4. Deletes the row (RLS gates to owner)
5. Deletes the storage file via `supabase.storage.from('hero-thumbnails').remove([path])`
6. Logs but doesn't fail if storage delete fails (row is already gone — better
   to have an orphan than a broken row reference)

Returns `{ success: true } | { success: false; error: string }`.

Order is deliberate: row first, storage second. If row delete fails, nothing
changes. If storage delete fails after row succeeds, log and continue —
acceptable orphan vs. broken state.

### Task 2: Clean up the existing test orphan

**One-shot script** to remove the orphan from the autonomous-test session:
`hero-thumbnails/5d840563-087c-41ae-9c70-b1bb19371759/6347c426-2780-4fa8-ab63-8e738e30befa.png`

Use the Supabase admin client via a tiny Node script (or `npx` invocation) so
this isn't blocked by `storage.protect_delete()`.

## Verification

- TypeScript: `npx tsc --noEmit` passes for the changed file
- Storage check: `SELECT count(*) FROM storage.objects WHERE bucket_id = 'hero-thumbnails'` returns 0 after cleanup
- (Manual, optional) call the new server action against a freshly-published
  carousel and verify both the row and the file are gone

## Blockers explicitly addressed (revision pass 1 — 2026-05-20)

### Blocker 1 — Live caption-card Y mirroring

The deleted chrome consumed `resolveCaptionBar(...).y` (the LIVE resolver
output) so it tracked user drags of the caption card. The naive adapter
fallback would have computed Y once from `template.captionCardDefaults.heightPct`
and frozen it — un-anchoring the kicker from the user-moved card.

**Fix:** `liveCaptionCardTopPct(overrides, template)` in
`src/lib/render/ruled-highlight.ts` mirrors `resolveCaptionBar`'s Y math
(`src/lib/render/resolve-overlay.ts:543-572`) WITHOUT importing the full
resolver. It honors:

- `caption_bar_y` (explicit drag)
- `caption_bar_height_pct` (height slider)
- `caption_bar_position` (top/bottom flip)

The adapter (`src/lib/editor/text-box-adapter.ts`) feeds the live cardTopPct
into `ruledHighlightTopPctFromCaptionCardY` for `position.y`. Test case 13 in
`text-box-adapter.test.ts` explicitly asserts the production-baseline data
(`caption_bar_y=67.3`, `caption_bar_height_pct=34`) lands the kicker at the
LIVE Y — NOT at the template default — via a dynamic anti-assertion (W2 fix).

### Blocker 2 — cc.enabled gate

The deleted chrome was hidden when `resolveCaptionBar(...).enabled === false`,
mirroring the chrome's `if (!cc.enabled) return null` guard. The naive
adapter fallback always injected the kicker on news-oracle covers, breaking
the "toggle caption card off → kicker off" behavior.

**Fix:** The D1 fallback branch is gated on
```ts
captionCardEnabled =
  o?.caption_bar_enabled === true ||
  (o?.caption_bar_enabled == null && o?.layout != null)
```
mirroring the chrome's `isNewsLayoutSlide` predicate for news-oracle (which
has `backgroundMode == null`). Test cases 14-17 in `text-box-adapter.test.ts`
cover the four gate corners; case 6a-6c in `ruled-highlight-parity.test.ts`
asserts the cc.enabled=false slide produces NO kicker text on any of the
three render surfaces.

## Architecture notes

### Adapter mirrors text_boxes → custom_texts

The renderers iterate `slide.custom_texts` for custom-anchored boxes (not
`slide.text_boxes`). To make the adapter-injected kicker visible on first
load — BEFORE the editor's `applyDualWrite` fires — both `migrateLegacySlides`
(use-slide-editor.ts) and the AI ingest paths (generate-slides.ts +
generate-from-style-spec.ts) now mirror the new text_boxes into custom_texts
via `textBoxesToLegacy`. This preserves TPLREND-05 / PARITY-01 (single source
of truth for the kicker via `RULED_HIGHLIGHT` geometry across three surfaces).

### Rule color follows tb.color (Warning 4)

All three render paths paint the flanking rules using
`tb.color ?? template.textColor` — the box's TEXT color — NOT
`effects.highlight.color`. Setting `tb.color='#FF0000'` and
`effects.highlight.color='#00FF00'` on a `'ruled'` box paints rules in
`#FF0000`. Adapter case 18 in `text-box-adapter.test.ts` and case 7 in
`ruled-highlight-parity.test.ts` cover this.

### Hook/body 'ruled' fall-through (Warning 5)

The `'ruled'` rendering is scoped to custom (accessory_label) boxes. A hook
or body TextBox carrying `style: 'ruled'` falls through to plain text on all
three surfaces — no rules, no pill, no error. Case 8 in
`ruled-highlight-parity.test.ts` proves this with W3's full anti-pill lock-down.

  <instructions>
    Write a single SQL migration. Postgres runs every `.sql` migration inside a transaction by default, so the ALTER and UPDATE are atomic without an explicit BEGIN/COMMIT. The order MUST be:

    1. `ALTER TABLE profiles ADD COLUMN onboarding_completed_at timestamptz;` — nullable, no default. New inserts after migration get NULL.
    2. `UPDATE profiles SET onboarding_completed_at = now() WHERE onboarding_completed_at IS NULL;` — backfill all existing rows in the same transaction so no user is briefly eligible to see the tour mid-deploy.

    Add a header comment block following the project convention (mirror `20260514_v213_phase80_style_spec_cache_v2_purge.sql`):
    - Phase 81 R1 reference
    - Why the order matters (column first, backfill second, same txn)
    - Why no RLS change is needed (existing profile-self RLS covers it)
    - Confirmation that new rows after this migration default to NULL (triggering the tour for genuine first-time users)

    Do NOT add a DEFAULT clause to the column — that would write a non-null timestamp into new rows and break SPEC R2 (auto-fire only when NULL).

    Do NOT add an index — the column is read once per dashboard load via the profile-self lookup which already uses `WHERE id = $user_id` (the PK). No new query shape that would benefit from an index.

    Do NOT touch any other table or any RLS policy.
  </instructions>

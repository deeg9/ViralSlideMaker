<objective>
Convert the sync code-only `getTemplate(id)` call sites that a DB `template_id`
can now reach (after Phase 87 wired DB templates into the picker + generation)
to the async DB-aware `resolveTemplate(id)` from the registry — closing WIRE-03.

Until this plan, a carousel saved on a DB template renders with the WRONG
template everywhere: `getTemplate` is code-only and silently returns
`templates[0]` (highlight-bar) for an unknown (DB) id. The render routes,
publish path, AI prompt, and generation server action all resolve the project
`template_id` through `getTemplate`.

`resolveTemplate(id)` (registry.ts, Phase 83) is the async code+DB resolver:
code-first (byte-identical to `getTemplate` for the 13 code ids), then DB rows,
then `templates[0]` fallback — exactly mirroring `getTemplate`'s unknown-id
contract. The conversion is therefore behavior-neutral for code ids.

Three classes of call site:
1. Render routes / publish (already in `async` contexts) → straight
   `await resolveTemplate(...)` swap.
2. `prompts.ts buildSystemPrompt` — consumed SYNCHRONOUSLY by 40+ tests and
   `generate-slides.ts`. It CANNOT become async without breaking all of them.
   Instead, the already-async caller (`generate-slides.ts`) pre-resolves the
   template and passes it in via a new optional parameter; `buildSystemPrompt`
   stays sync with a sync `getTemplate` fallback when the param is absent.
3. The editor canvas (`slide-editor.tsx`) is a `'use client'` component that
   resolves in its render body — it cannot `await`. Its server-component
   parent (`page.tsx`) pre-fetches DB templates and passes them down; the
   client resolves code-first then from the passed-in DB map.
</objective>

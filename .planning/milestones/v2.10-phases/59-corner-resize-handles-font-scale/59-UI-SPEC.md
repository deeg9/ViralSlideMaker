# Phase 59 — UI Design Contract: Corner Resize Handles + Font-Scale

> Visual and interaction contract for Phase 59. Generated by gsd-ui-researcher, verified by gsd-ui-checker. This phase is an interaction-polish phase, not a visual redesign — the contract is gesture-semantics-heavy and visually minimal.

---

## Scope

Phase 59 adds corner-drag-to-scale-font-and-width to text boxes (hook, body, custom) in the editor. The visible additions are intentionally narrow: 4 corner handles per active text box (12×12 visual, 24×24 hit zone) plus 2 modified cursor states (`nwse-resize`, `nesw-resize`). No new screens, panels, modals, dialogs, or pages. No new colors, fonts, design tokens, or copywriting elements. The interaction contracts ARE the design contract — gesture semantics, hit-zone WCAG compliance, undo discipline, and right-rail slider sync are what this UI-SPEC pins down. Editor-only render path; Satori PNG export and the non-editable preview branch (`slide-preview.tsx:559`) are untouched by design.

## Handle Visual Treatment

The corner handle visual is anchored to the existing custom-image handle precedent at `slide-preview.tsx:1152-1188`. That block already proves all 8 handles render correctly under the CSS-`transform: scale()` parent and is the design pattern this phase mirrors with one substitution: the visual size goes from 8×8 to 12×12 (WCAG-compliant visual + Figma small-handle aesthetic) and the offset goes from `-4` to `-5` to keep the handle visually centered on the box corner.

### Per-handle style

```ts
const cornerHandleStyle: React.CSSProperties = {
  width: 12,
  height: 12,
  backgroundColor: 'rgba(255, 255, 255, 0.95)', // matches custom-image (1156)
  border: '1px solid rgba(0, 0, 0, 0.35)',      // matches custom-image (1157), slightly stronger contrast
  borderRadius: 2,                              // matches custom-image (1158)
  position: 'absolute',
}
```

### Per-position offsets

Each corner handle sits with its visual center on the box corner:

| Handle | Position offsets |
|--------|------------------|
| `topLeft` | `top: -5, left: -5` |
| `topRight` | `top: -5, right: -5` |
| `bottomLeft` | `bottom: -5, left: -5` |
| `bottomRight` | `bottom: -5, right: -5` |

### Side handles — preserved unchanged

Existing left/right side handles keep today's `resizeHandleStyle` definition (slide-preview.tsx:231-239): `4×40` white-translucent vertical bar, vertically centered, `left: -2` / `right: -2`. NO visual change to side handles in this phase.

### Z-order & rendering gate

Handles render only when:
1. `editable === true` (the `<Rnd>` wrapper itself is editor-only — slide-preview.tsx:559 returns before any `<Rnd>` mounts in the non-editable branch).
2. The text box matches `selectedTextBoxId` (single-element selection is the v2.8 contract). Other text boxes show only the existing hover outline; corner handles do NOT appear on unselected boxes.

### State variants

| State | Treatment |
|-------|-----------|
| Default (selected, not hovered) | Per spec above — 12×12 white-translucent square with 1px dark border |
| Hover | No visual change to the handle itself. Cursor changes per cursor table below. |
| Active drag | No visual change. react-rnd's internal positioning takes over; the handle moves with the corner. |
| Disabled | Not applicable — handles are either rendered (selected box) or not rendered (any other state). |

## Cursor Affordance Contract

Cursor changes on handle hover are the primary discoverability affordance for this phase (per pre-PMF anti-feature lock-out: ONBOARD-01 — no first-use toast). The `<Rnd>` wrapper's inner content keeps `cursor: 'grab'` (slide-preview.tsx:1107 precedent for custom text); the handle wrappers must take precedence on hover.

| Handle | CSS `cursor` value | Visual semantics |
|--------|--------------------|------------------|
| `topLeft` | `nwse-resize` | NW ↔ SE diagonal arrow |
| `bottomRight` | `nwse-resize` | NW ↔ SE diagonal arrow |
| `topRight` | `nesw-resize` | NE ↔ SW diagonal arrow |
| `bottomLeft` | `nesw-resize` | NE ↔ SW diagonal arrow |
| `left` | `ew-resize` (preserved — react-rnd default) | E ↔ W horizontal arrow |
| `right` | `ew-resize` (preserved — react-rnd default) | E ↔ W horizontal arrow |
| `top`, `bottom` | not applicable — `enableResizing.top = false`, `enableResizing.bottom = false` | no handle, no cursor |

**Implementation:** apply `cursor: 'nwse-resize'` (or `'nesw-resize'`) inline on each corner handle's style object, NOT via CSS class. The handle wrapper's inline style wins over any parent's `cursor: 'grab'` because inline styles trump class-based rules at the same specificity.

## Hit Zone (WCAG 2.5.8 AA)

Visual handles are 12×12. Hit zones must be at least 24×24 CSS pixels per WCAG 2.5.8 AA (`https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html`). The 6px-per-side gap is closed via an invisible padding wrapper.

### Pattern: invisible wrapper via `inset: -10px` on a wrapper element

Two equivalent options — pick one consistently in C1:

**Option A (preferred — simpler):** wrap the visual square in an absolutely-positioned wrapper with negative inset:

```tsx
<div style={{
  position: 'absolute',
  inset: -6,           // extends 6px past the visible square in every direction
  cursor: 'nwse-resize',
  // 12 + 6 + 6 = 24 hit zone
}}>
  <div style={cornerHandleStyle} />
</div>
```

Total hit area: `12 + 2×6 = 24px` per axis. Meets WCAG 2.5.8 AA.

**Option B:** `::before` pseudo-element with `inset: -6px`. Equivalent semantically; pick the one that integrates cleanest with `react-rnd`'s `resizeHandleStyles` prop (Option A is closer to react-rnd's existing handle-style API).

### Canvas-scale awareness

At the editor's typical canvas scale of `~0.4`, a 24px CSS hit area renders at ~60px in viewport pixels (24 / 0.4). This is acceptable — bigger touch targets are better on mobile, and the wrapper is editor-only so it never reaches the Satori export (PARITY-02 invariant preserved by construction).

### Don't fall through to the smaller hit zone

If react-rnd's default handle wrapper element is what receives pointer events, the 12×12 visual + 6px padding wrapper described above must wrap or replace that default — confirm via DevTools that hovering 8px outside the visual square still shows the resize cursor. If it doesn't, the wrapper is being painted but isn't catching events — fix the structure before claiming A11Y-01 passes.

## Gesture Semantics

The Canva-style hybrid is locked from `/gsd-new-milestone` (CONTEXT.md "UX semantic — LOCKED"). This table is the authoritative input → output contract:

| Gesture | Width changes? | `font_size` changes? | Notes |
|---------|----------------|----------------------|-------|
| Corner-drag (TL, TR, BL, BR), no modifier | Yes — `position.width` updated | Yes — scaled proportionally to width ratio | Default behavior. Formula: `new_size = clamp(round(old_size × (new_width_pct / old_width_pct)), role_min, role_max)`. Bounds: hook `[16, 240]`, body `[14, 120]`, custom `[14, 120]`. |
| Corner-drag with **Shift** held | Yes — `position.width` updated | **No** — font unchanged | Width-only escape hatch (RESIZE-04). Read `e.shiftKey` in `onResizeStop`. Matches Figma/Canva muscle memory. |
| Side-drag (left, right), any modifier | Yes — `position.width` updated | **No** — font unchanged | Preserves v2.8 muscle memory exactly. No regression. |
| Top or bottom drag | n/a | n/a | Not possible — `enableResizing.top = false`, `enableResizing.bottom = false`. No handle rendered. |
| Corner-drag past the role cap (240 hook / 120 body / 120 custom) | Yes — box keeps growing | Caps at the role max | Past-cap forgiveness: drag never feels "stuck." Box width grows freely; font_size clamps. |
| Corner-drag below the role floor (16 hook / 14 body / 14 custom) | Yes — box keeps shrinking down to its `minWidth` clamp | Caps at the role min | Symmetric to past-cap. `position.width` is independently clamped at the existing `Math.max(20, ...)` floor (slide-preview.tsx:896). |
| `onResize` ticks (every pointermove during drag) | n/a | n/a | NO dispatch. react-rnd manages transient visual state internally. No history entry. No store mutation. |
| `onResizeStart` | n/a | n/a | Capture `oldWidthPx` and `oldFontSize` into refs. NO dispatch. |
| `onResizeStop` (gesture commit) | One dispatch | One dispatch (skipped if Shift) | Single atomic write. Both writes round-trip through the existing reducer in one history entry (UNDO-01). |

### Bounds reference (read-only — no UI-SPEC change)

```
hook   font_size: clamp [16, 240]   width: clamp [20%, 100%]
body   font_size: clamp [14, 120]   width: clamp [20%, 100%]
custom font_size: clamp [14, 120]   width: clamp [20%, 100%]
```

Slider min/max already pinned at `ActiveTextBoxCard.tsx:256-257`. Phase 59 must not exceed these bounds — if drag math yields a value outside the slider's range, the slider would silently lie. Clamp before dispatch.

## Feedback Contract

### Right-rail font-size slider sync

**Single source of truth:** the slider at `ActiveTextBoxCard.tsx:259` reads `textBox.font_size`. The corner-drag dispatch writes the same `text_boxes[i].font_size` field. Therefore:

| Event | Slider state | Timing budget |
|-------|--------------|---------------|
| User starts corner-drag | Unchanged (slider holds `oldFontSize`) | n/a |
| User drags (every `onResize` tick) | Unchanged — react-rnd's transient state is local; reducer is not mutated | n/a |
| `onResizeStop` fires | Slider re-renders with `newFontSize` after one React render cycle | **≤ 1 frame (~16ms)** after `onResizeStop` callback returns |
| Subsequent slider drag | Writes the new value back through the same `font_size` field | preserves single-source-of-truth |

The 1-frame budget is achievable because the dispatch happens on `onResizeStop` (synchronous), the reducer mutation is synchronous, and React 19's render commits within the same frame for state updates that don't trigger Suspense. No `requestAnimationFrame` round-trip is needed.

### Undo discipline

| Gesture | Pointer ticks | History entries |
|---------|---------------|-----------------|
| 1 corner-drag (60-tick simulation) | 60 | **1** |
| 1 side-drag | any | **1** |
| 1 corner-drag with Shift | any | **1** |
| 1 corner-drag past cap | any | **1** (font caps inside the single dispatch; no extra entry) |

UNDO-01 invariant: dispatch ONLY on `onResizeStop`, never on `onResize`. Test pinned in C3 at `editor-reducer.test.ts`.

### Visual reflow

Text reflow during drag is handled by `<Rnd>`'s internal visual state (line-wrap recalculates as width changes). After `onResizeStop`, the next render reads the persisted `font_size` + `position.width` and the box redraws to match. There must be no visible "snap" or "jump" between the end-of-drag visual and the post-commit render — the values must be identical at both moments.

### No mid-drag UI surfacing

No live numeric readout chip ("Hook 142px") in v2.10 — that's a `differentiator` from FEATURES.md, not table stakes, and pre-PMF cursor change is enough discoverability. Locked out by CONTEXT.md.

No alignment guides during corner-resize — `useAlignmentGuides` runs on `onDrag` only today; corner-resize snap is GUIDES-01 deferred to v2.11.

No first-use toast — ONBOARD-01 deferred.

## Out of Scope

This UI-SPEC deliberately does NOT cover:

- **Top/bottom resize handles or any vertical resize affordance.** `enableResizing.top = false`, `enableResizing.bottom = false`. No handle rendered, no cursor binding, no gesture semantics. (RESIZE-05, HEIGHT-01, MIN_HEIGHT-01 — locked out per CONTEXT.md `<deferred>`.)
- **Rotation handles.** Out of scope for v2.10 (ROTATE-01, defer to v3.0+).
- **Aspect-ratio-lock toggle in the right rail.** Shift+corner = width-only escape hatch covers the use case (ASPECT-01 deferred).
- **Multi-select group resize.** Single-element selection is the v2.8 contract (MULTISELECT-01 anti-feature).
- **Snap-to-alignment-guides during corner-resize.** `useAlignmentGuides` runs on `onDrag` only; corner-resize snap is v2.11 candidate (GUIDES-01).
- **First-use onboarding toast for the corner-drag gesture.** Pre-PMF, cursor change is enough discoverability (ONBOARD-01 deferred).
- **Live numeric readout chip during drag** ("Hook 142px"). Differentiator, not table stakes (FEATURES.md "Differentiators" — defer).
- **Auto-fit-text-to-box-on-type / Magic Resize.** Conflicts with the explicit slider model (AUTOFIT-01 anti-feature).
- **Skew / shear handles.** Anti-feature for social-content layouts (SKEW-01).
- **Visual change to side handles.** Side handles preserve their existing 4×40 vertical-bar visual exactly. Phase 59 only adds 4 corner handles.
- **Cursor change for the inner draggable area.** The inner `cursor: 'grab'` (slide-preview.tsx:1107 precedent) stays unchanged. Only the corner handle wrappers get the resize cursors.
- **Touch a11y for any other element.** A11Y-01 covers resize handles only.
- **Pixel-precise W/H input fields in the right rail.** Not in v2.10 (deferred per PITFALLS.md #17).
- **Custom-image handle changes.** `slide-preview.tsx:1152-1188` is the precedent we MIRROR; we do not modify it. Image handle visual stays at 8×8. (FEATURES.md Open Q #6 — leave image behavior unchanged.)
- **Custom-text dispatch path cleanup** (`slide-preview.tsx:1062` still calls `UPDATE_CUSTOM_TEXT`). CLEANUP-01 — punted to a future quick.

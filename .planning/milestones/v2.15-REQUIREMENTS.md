# Requirements — v2.15 DB-Backed Template Wiring

**Milestone:** v2.15 DB-Backed Template Wiring
**Defined:** 2026-05-19
**Source:** `.planning/DB-TEMPLATE-WIRING-SPEC.md` (feature spec — verified
file-level blast radius, recommended 2-phase breakdown)

Goal: make a v2.14 DB-backed template usable end-to-end — pickable in the
generation picker, preserved through generation, rendered identically across
all three render paths, and preserved through publish/fork — closing v2.14's
TSTORE-02 / TSTORE-03, which passed only as isolated unit tests because Phase
83's merged registry was built but never wired into the app.

Prior-milestone requirements are archived at
`.planning/milestones/v2.14-REQUIREMENTS.md`.

---

## v2.15 Requirements

### Template Wiring (WIRE)

- [ ] **WIRE-01**: DB templates appear in the generation picker — fetched
  server-side, merged with the selected category's code templates, filtered by
  the `templates.category` column, and rendered with their preview-PNG tiles
  via `TemplateTilePreview`.
- [ ] **WIRE-02**: Generation preserves a selected DB template id — the
  category-snap logic in `generation-form.tsx` (initial state + category-change
  handler), `project/[id]/actions.ts`, and `services/carousel.ts` no longer
  discards a DB template id whose `category` matches the selected category; the
  carousel API validates the submitted id via `isKnownTemplateId`.
- [ ] **WIRE-03**: All three render paths — canvas preview, Satori PNG export,
  HTML export — resolve a DB `template_id` via async `resolveTemplate` instead
  of the sync code-only `getTemplate`; a DB-template carousel renders identically
  across all three (TSTORE-03 true in the running app, not just unit tests).
- [ ] **WIRE-04**: A per-slide `template_id_override` accepts a DB template id
  instead of rejecting it against the code-only `TEMPLATE_IDS` allowlist.
- [ ] **WIRE-05**: Publish and fork preserve a DB `template_id` — a published
  DB-template carousel keeps its `template_id`, a fork inherits it, and both
  render correctly.
- [ ] **WIRE-06**: The 13 code templates and the ~82 existing carousels stay
  byte-identical — `legacy-templates-byte-identical`, `legacy-templates-regression`,
  `new-templates-parity`, and the render-parity fingerprint suites stay green.

## Future Requirements (deferred)

- End-user / community template authoring, and the picker surfacing
  community-published templates.
- Editing or deleting a saved DB template — still save-new-only.
- Explicit registry cache invalidation on template write (v1 accepts the
  ≤60s TTL).

## Out of Scope

| Excluded | Reason |
|----------|--------|
| New template authoring capability | v2.14 already shipped the admin Save-as-Template flow + the `flat_style` capture fix (commit `1c87c79`). |
| `LayoutRecipe` model / extraction / recipe-driven generation logic | Shipped in v2.14 (Phases 84/85); v2.15 only makes a DB recipe template *reachable* so that logic actually runs. |
| Migrating the 13 code templates into the DB | Code templates stay in code for back-compat; DB storage is additive. |
| Schema migration | The `templates` table + `category` column already exist (Phase 83); v2.15 is app-layer wiring only. |
